# SETU Mesh — ACK Lifecycle

Owner: Vib (Mesh/Architecture). Based on direct source reading of
`lib/mesh/services/mesh_service.dart`, `lib/core/services/mesh_locator.dart`,
`lib/mesh/models/ack_packet.dart`, as of the Sep 21 2026 mesh-hardening pass.

## Current Implementation

### Path
```
Origin device: originate(EmergencyPacket)
  → enqueued (LocalQueueService) + sent over Nearby (MeshServiceImpl.originate)
  → _tryUpload() fires immediately if this device itself has internet

Any relay hop: _handlePayload() → validate → verify signature → _relayPacket()
  → AckPacket is relayed exactly like any other packet type (no special
    priority, not gated by ResponderRegistry — see ack_packet.dart's own
    docstring for why: acks are not a privileged action)

Exit node (whoever first gets internet, self or a relay):
  _tryUpload() or _retryPendingUploads() → backend accepts
  → _markPacketDelivered() → if packet is EmergencyPacket, _originateAck()
    is called, which itself goes through the normal originate() path (so
    the ack is sent, persisted, and — if the exit node also has internet —
    immediately "uploaded" too, though an AckPacket is explicitly excluded
    from _tryUpload at its very first line: `if (packet is AckPacket ...) return;`)

Ack travels the mesh back like any packet. Any device whose
_originatedEmergencyIds set contains the ack's emergencyId surfaces it on
its `acknowledgments` stream (mesh_service.dart, inside _handlePayload's
AckPacket branch).

MeshLocator's acknowledgments listener (core/services/mesh_locator.dart)
updates BOTH HistoryRepository and RecoveryRepository by emergencyId,
unconditionally, on every ack — both lookups are no-ops when nothing
matches, and a given emergencyId can only belong to one or the other
(see "Identity" below for the caveat on this assumption).
```

### emergencyId stability
`emergencyId` is set once at packet creation (`emergencyId: packetId` for
both `EmergencyPacketBuilder` and `RecoveryPacketBuilder`) and is never
mutated by `withRelayHop()` on any packet subtype — only `ttl`/`hopCount`
change per hop. Confirmed stable end-to-end.

### Matching
- Origin-side ("is this ack mine"): `_originatedEmergencyIds.contains(ack.emergencyId)` — a `Set<String>` populated on `originate()`, string equality only.
- Local-status-side (History/Recovery): `entry.emergencyId == ack.emergencyId` — also string equality.

## Native Layer (Bulk Sprint 2 correction)

The "Any relay hop" step above ("AckPacket is relayed exactly like any
other packet type") is confirmed true one layer deeper than Sprint 1 could
verify: native Kotlin's `PacketRelayEngine.process()` has **no special
case for ack packets at all** — an `AckPacket`'s bytes are just another
JSON blob to dedup-check, TTL-decrement, and relay. Native also **never
generates an ack itself** — `_originateAck()` is Dart-only, confirmed by
grepping all 8 native files for ack-construction logic and finding none.
This means: while a device is backgrounded with only the native service
alive, it will faithfully relay an ack it receives, but it cannot
originate a new one — ack generation only happens when Dart is attached
and processes a payload through `_handlePayload`. See
`NATIVE_MESH_AUDIT.md` §9–§10.

## Known Limitations (honestly stated, not fixed this pass)

1. **`_originatedEmergencyIds` grows unbounded for the life of the process**
   — entries are added on every `originate()` call and never removed. Not
   exploitable (bounded by how many emergencies one device originates in
   one app session, realistically small), but noted as a minor leak.

2. **emergencyId is generated by the same formula in both builders**
   (`"$shortSenderId-$microsecondsSinceEpoch"`), with no domain separation
   between an SOS packet and a Recovery packet. On a platform where
   `DateTime.microsecondsSinceEpoch` only resolves to millisecond
   granularity, two packets built by the same device in the same
   millisecond (e.g. an SOS immediately followed by a recovery report)
   could theoretically collide. Not proven to happen in this codebase, and
   not fixed this pass — the correct fix is a proper collision-resistant ID
   scheme, which is a bigger change than this hardening pass's scope
   allows without more evidence it's a real problem.

3. **Retry-path ack gap — FIXED this pass.** Previously, `_retryPendingUploads()`
   marked a packet uploaded but never called `_originateAck()` — only the
   immediate `_tryUpload()` path did. A packet delivered exclusively via
   the 30-second retry loop (e.g. the device had no internet at the moment
   it first received/originated the packet) never acked the sender. Both
   paths now share `_markPacketDelivered()`, which always originates an ack
   for an `EmergencyPacket`. See `MESH_HARDENING` commit for the diff.

4. **Concurrent double-upload — FIXED this pass.** `_tryUpload()` and
   `_retryPendingUploads()` could both attempt to upload the same
   `packetId` concurrently if the 30s timer fired while an immediate
   upload for that packet was still in flight. A `_uploadingPacketIds`
   in-flight guard now prevents this at the client level. This does not
   depend on (or replace) backend-side idempotency — it just stops the
   Dart layer from being a source of duplicate submissions.
